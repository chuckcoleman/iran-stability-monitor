# Iran assessment — reviews before GitHub publication

## V9 source-access provenance: distinct stages, not automatic contradictions

New live `research-dry-run` sessions use the **V9** immutable source
snapshot; every V1–V8 research prompt, paid API fingerprint, frozen cutoff
and previously saved source-review result remains unchanged.

For **every canonical original-source URL**, the screened V9 packet has
`v9_access_channels` with three independent provenance streams:

1. **Earlier research model's search-stage access statement and limitations.**
   This is preserved text from the original paid model output and bound to
   its SHA-256, **not** an independent HTTP access log.
2. **Later Python metadata HTTP probe.** Its actual retrieval/access status,
   original parser status, and publisher-supplied time are recorded without
   claiming full article-body inspection or proven first publication. It may
   legitimately succeed after a search-stage request was reportedly blocked,
   or fail after a search-stage response was apparently readable.
3. **Separately retrieved exact original-body passage witness**, where
   available. Its narrow hash/source identity does not authenticate the
   event, geopolitical effects, the publisher's claimed first release, or
   any uncaptured article body.

Do not call differences between independent access *stages* automatic
contradictions or claim that one proves access success in the other stage.
Do not silently reconcile or discard real same-stage errors. Both independent
affirmative and critical reviewers must explicitly compare the channels,
state how access inconsistencies were investigated, and retain exact original
URLs for any genuine unresolved material access discrepancies. If either
reports an unresolved discrepancy, or the provenance hashes/fields fail
machine validation, the source audit **cannot** be marked complete.

The six-category research sweep, no accepted-evidence count quota,
original-source and cutoff guards, exact previous reviewer verdicts,
no-repeat-paid-POST safety and **NOT PUBLISHABLE** policy are unchanged.
Audit-only completion can remain **inconclusive for national forecasts**;
it never authorizes new forecasts, website updates or X publication.


## Forward-only V8: separate source-audit completion from forecast inference

New, explicitly launched research-dry-run diagnostics use the V8 frozen source
snapshot and independently reported **two-axis** source review. Prior V1–V7
research snapshots, paid research and reviewer prompts, original API response
IDs, archive hashes and historic failed decisions are never retrospectively
rewritten or recertified.

The **source audit** answers whether all six original-source search categories,
all listed URLs, exact attribution/citation records, access and publication
uncertainties, historical context, held evidence, and the original evidence
cutoff were accurately documented. Publisher article metadata, including a
timezone-aware datePublished field, is *publisher supplied*: not independently
verified first publication. Fetching an HTML metadata page never by itself
establishes original full-article inspection. An exact original-page passage
register is a separate, narrower witness, not verification of event truth.
Later metadata checks do NOT expand the original research as-of interval.

The distinct **geopolitical inference** decision asks whether admissible
source observations support any prospective national-stability conclusion.
There is no accepted-evidence count or publisher quota. A complete source
audit may legitimately report **zero** supported observations, with an
inconclusive geopolitical inference.

Only when both affirmative and critical reviewers independently confirm an
accurate, complete audit, reconcile the exact source count and six categories,
and each records *only* the specific insufficient-inference objection does
the read-only diagnostic stop as
`RESEARCH_AUDIT_COMPLETE_INCONCLUSIVE_NOT_PUBLISHABLE`. This is a completed
**audit-only** outcome, not approved evidence for forecasts, not a clean
geopolitical forecast, not a Sunday assessment receipt, and never a website
or X authorization. Any unresolved source-access, first-publication,
citation, chronology, attribution, coverage, or review conflict continues
to **fail the audit**; a favorable top-level label cannot waive it.
Failed audit checks, missing reviewer fields, timeouts, unreviewed sources
and contradictory dispositions remain fail-closed. The two reviewers are
still required on the **identical hashed packet** and no new paid correction
round is scheduled after a valid audit-only inconclusive terminal decision.

## Long-running Responses API requests and failure recovery

Research web searches are now created with OpenAI Responses **background=true**
and **store=false**, then polled by their acknowledged response ID with bounded
read-only GET requests. The first POST is issued **exactly once**: if its
acknowledgement is lost or the connection closes, the run stops with an
explicit **unknown-acceptance / DO NOT REPOST** diagnosis. Once a response ID
is known, intermittent GET failures permit limited retrieval retries against
the **same ID**; an incomplete/failed/cancelled response, missing ID or exhausted
time limit is a failure, never a clean forecast or source review. The
non-search assessment and reviewer JSON calls retain their existing
foreground request protocol, strict JSON validation and single-submission rule.

Before requesting a bearer token or sending each API POST, the script creates
a durable, redacted `api-request-*.json` record in the ignored
`.automation-audit` directory (or designated external review audit
directory). It contains only response/request identifiers, a SHA-256 request
fingerprint, stage/model, known transport status, retry counts and timestamps:
**never raw prompts, authorization headers, WIF credentials, signed JWTs or
API error bodies**. The diagnostics workflow uploads these records even if
the live API fails before any response is returned. A record saying the
remote API completed is *not* a valid research ledger or editorial approval;
the existing source-citation, evidence cutoff and response-JSON checks must
all pass separately. No automatic POST resubmissions are permitted.

OpenAI background store=false responses are temporarily retained for polling
(about ten minutes under the documented policy), not archived indefinitely.
This project enforces a bounded ~9-minute research poll interval to avoid
mistaking expired responses for approval. An unresolved response ID may be
inspected using authorized API retrieval, but MUST NOT cause an automatic
new billable generation. This implementation changes no archived forecasts,
frozen forecasting event definitions, branch protections or publication gates.

## October 13: alternating affirmative and critical reviews — current publication gate

Every newly prepared Sunday assessment receives alternating **affirmative** and
**critical** reviews of the *same exact draft*, in that order. The affirmative
review independently verifies evidentiary support, balance, documented
assumptions and qualifications; the critical review independently challenges
weak claims, missing evidence, contradictions, double counting, forecasts,
warnings and data quality. Neither reviewer may infer that a favorable verdict
from the other reviewer is sufficient.

Publication requires **both** reviewers to return a valid, explicit
`approved: true` verdict with an **empty** `issues` array on the **same
unchanged draft**, after deterministic data and frozen-Protocol-v1 checks.

correction and then a **fresh affirmative-and-critical pair**, even if one
reviewer previously approved an earlier draft. An approved draft is not
automatically approved again after a change.

Review is bounded by **six full cycles** (initial draft plus at most five
revisions) and a **60-minute review-phase deadline**, inside the existing
90-minute GitHub Actions job deadline. Those are *resource limits*, not
success criteria. If clean consensus is not reached, the workflow **fails
closed** without pushing, merging, deploying, or posting. API errors, malformed
or contradictory review verdicts, incomplete review stages, reviewer or runner
timeouts and process cancellation are also **failures, never passes**.
Individual review results are retained in dated, role-labeled run audit files
with the exact draft SHA-256; the final receipt is written only after both
reviewers approve the same SHA-256 and all deterministic checks pass.

The report's four core prospective forecasts are elicited exactly once per

## What a live run does

- Retains exact original history bytes and hashes the frozen inputs. Uses actual
  current reporting, captures accessible article `datePublished` metadata before
  cutoff, and retains source hashes and retrieval times. Model-inferred publication
  clocks are never substituted for verified metadata. Missing or contradictory
  precise times remain unknown; known later sources block the record. Citation
  presence is a provenance check, not independent proof that every claim is true.
- Closes research, records the real cutoff, then elicits exactly four core forecasts
  with web access disabled. A separate no-web review may reject but cannot silently
  revise them. Complete diagnostic scenario partitions are elicited, not generated
  from arbitrary multipliers. Genuine zero revisions may use explained zero
  contributions rather than invented offsets. Declared residuals must reconcile.
- Reuses persistent evidence identities across the archive; applies the frozen
  warning rubric, Houthi rule, six oil-credit components and 0/20/40 sensitivity.
  Monthly Hanke analysis retains a separately identified underlying observation
  date; intermediate Sundays carry the monthly diagnostic forward.
- Requires schema, Protocol validator, offline tests, JavaScript syntax, and
  dashboard-field consistency. No old record or root field may change. Only the
  new, not-yet-committed record receives a captured issuance time; that time equals
  the candidate Git commit's author/committer timestamp. Actual later public
  deployment is independently attested, not backdated.
- Research runs after the GitHub App's initial permissions/safety preflight, but
  before a fresh App installation token is minted for publication. Commits only
  `data/history.json` on a dated branch, opens a PR, waits for the correct Actions
  `validate` job at its exact head SHA, checks `main` again, then merges without
  bypass. GitHub App-authenticated writes trigger CI/deployment unlike writes
  authenticated by the default `GITHUB_TOKEN`. Transient push credentials remain
  process-scoped rather than stored in a Git remote URL or checkout settings.
- Requires successful `validate` and **Deploy validated website** jobs from the
  correct main push workflow and SHA. Checks that the full canonical public JSON
  matches and is not superseded. An attestation records date, SHA, run ID and
  history hash. A code-only merge does not announce a new assessment.
- Re-verifies before X with a distinct newly minted installation token; checks **scheduled posts and the separate published-X CSV**.
  A unique Git tag `x-announcement-YYYY-MM-DD` atomically reserves the date before
  the non-idempotent Metricool POST. Old issue-based claims remain respected.

## Failure and recovery

A failed evidence, clock, arithmetic, archival, CI, permission, source or merge-base
check leaves the candidate unmerged. A failed gated deployment leaves the previous
successful site in place, although the new merge remains in `main`. A social error
does not roll back a validated site.

If a Metricool POST times out or returns an uncertain acknowledgment, the persistent
Git claim remains and automatic retries stop. This is **at-most-one automatic
attempt**, not a claim of exactly-once external delivery. Reconcile the brand's
scheduled and published posts before any manual retry. Do not delete a successful
or uncertain posting tag to silence an error.

Source/issuance artifacts retain 30 days; publication receipts retain 90 days; PR
review-source artifacts retain 7 days. Public history remains in Git. Audit artifacts
contain public evidence and generated judgments, not API keys or full news articles.
Do not publish artifacts from a dry-run as scored forecasts.

Unfamiliar API response schemas fail closed rather than treating missing fields as
success. Readiness detects many permissions/format issues, but subscription or
service changes may still require maintenance. No software can guarantee the truth
of automated geopolitical judgments solely from schema tests or model review.
